# fixtures — the record library

One job: hold the synthetic source-harness repositories that pin dshify's behaviour. Each fixture is a **record**: a folder with the same shape, created by copying the stamp, never by starting from a blank page.

## Inputs

- Reference (every run): `../docs/spec.md` — §13 is what fixtures exist to prove
- Reference (every run): `_templates/opencode-fixture/` — the stamp every new record is copied from
- Working (this run): `_index.md` — the generated catalog (one line per record, with status)
- Do NOT load: `../test/` internals, or every record's fixtures when adding one

## Rules

- **Small and boring.** A fixture pins one behaviour; it is not a showcase.
- **Synthetic only.** No third-party repository content, no real tokens, no URLs with credentials. `.example.test` hosts only.
- **Committed.** The fixture is the input half of a golden test; the expected output is generated by the test and reviewed in the PR.
- **One behaviour per fixture.** `opencode-basic` is the happy path; collision, malformed and auth records isolate the ugly paths.
- **Never mutate during a test run.** Tests copy a record into a temp directory before scanning or applying.
- **`_templates/` is not a record.** Tests enumerate records from the catalog, never by globbing `fixtures/*`.

## Record shape

A record is a directory named `<harness>-<case>/` containing:

```text
<harness>-<case>/
├─ CONTEXT.md              the record: status, coverage, what it pins (dshify metadata)
├─ opencode.json           source-harness config (roots, MCP)
├─ AGENTS.md               workspace instructions
├─ .opencode/skills/<id>/SKILL.md
├─ .opencode/commands/<id>.md
├─ .opencode/agents/<id>.md
├─ skills/<id>/SKILL.md    optional extra configured root
└─ .agents/skills/<id>/SKILL.md   optional already-native skill
```

`CONTEXT.md` sits at the record root and is **dshify metadata, not source-harness content** — no configured root points at the fixture root, so the adapter never reads it. Its frontmatter carries `status`, `verified` and `covers` (the spec §13 items the record proves).

Expected outputs are **not** stored inside the record — they go to `test/golden/<harness>-<case>/` once the emitter exists (P2). Putting them here would mean the scan reads its own expected output.

## Adding a record

1. Copy `_templates/opencode-fixture/` to `fixtures/<harness>-<case>/`.
2. Fill `CONTEXT.md`: purpose, the one behaviour, `covers:`.
3. Keep every file tiny; no real hosts or credentials.
4. Regenerate the catalog: `python3 -I _tools/index.py fixtures`.
5. Run `bash _tools/walk-test.sh` — a record without `CONTEXT.md` fails.

## Check

`bash _tools/walk-test.sh` asserts every record has a contract, and that a declared golden path exists. A reviewer confirms the record is synthetic, tiny, and proves exactly the one behaviour it claims.
